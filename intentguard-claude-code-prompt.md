You are my engineering partner on **IntentGuard**, which is both (a) an open-source runtime security framework and (b) the software behind a research paper. Treat it as two linked deliverables: a usable framework, and a reproducible experiment that can be defended in peer review.

## 1. What IntentGuard is

**Title:** Intent-Aware and Behavioural Authorization for Autonomous AI Agents: A Runtime Framework for Preventing Unauthorized Tool Execution and Sensitive Data Exfiltration.

**Core question:** Can an agent's tool call be authorized based on the user's original intent, the resources involved, the accumulated risk of earlier actions, and the permissions actually granted?

Existing controls ask "may this agent use this tool?". IntentGuard also asks "is *this specific action* justified by the user's task?".

**Hypothesis H1:** An intent-aware, cumulative-risk authorization framework reduces unauthorized agent actions versus conventional tool-permission controls, while keeping legitimate task completion acceptable.

Research questions:
- RQ1: How well can natural-language user intent be translated into enforceable authorization policy?
- RQ2: Can multi-step behavioural analysis catch attacks that per-call inspection misses?
- RQ3: Does dynamic permission reduction lower exfiltration success?
- RQ4: What is the latency and task-completion cost of the extra checks?

## 2. Non-negotiable design principles

1. **The gateway is not optional.** Protected tools are reachable only through the IntentGuard gateway. The agent process must have no direct handle to them (separate process/container boundary, tools registered only inside the gateway). Add a test that proves a direct call fails.
2. **Deterministic policy makes the final decision.** An LLM may *help* interpret ambiguous intent into a structured `TaskScope`, but it never has final say on sensitive access. If the LLM is unavailable or low-confidence, fall back to the stricter deterministic result (deny or require approval). The whole system must run end-to-end with the LLM disabled.
3. **Fail closed.** Errors, timeouts, and unknown tools resolve to deny or review, never allow.
4. **Log observable actions, not reasoning traces.** Record tool name, arguments, resource metadata, destination, decision, and the policy evidence. Do not store raw chain-of-thought.
5. **Every decision is explainable:** the exact rule IDs that fired plus structured evidence, never a generic "threat detected".
6. **Unusual is not malicious.** Track false positives on benign-but-unusual workflows as a first-class metric.
7. **Never claim 100% protection** anywhere in code, docs, or the paper draft.
8. **Safety of the research itself:** synthetic data and mock/isolated services only. Never contact real external hosts, accounts, or people. The mock "external upload" service and the "unknown domains" are local fakes. Block real network egress inside the experiment sandbox.
9. **No invented results.** Any results table you produce must be generated by actually running experiments. Where a number has not been measured, print `TO MEASURE`. Never hand-write benchmark numbers into docs, the dashboard, or the paper.

## 3. Architecture to build

```
User (task + granted permissions)
   -> Agent (LangGraph, or a scripted/deterministic agent for experiments)
   -> IntentGuard Gateway
        1. Action Interceptor        (tool, params, agent id, resource, destination)
        2. Intent & Context Analyzer (task scope vs. action, prior actions)
        3. Risk & Behaviour Engine   (sequence risk, sensitivity, cumulative score)
        4. Policy Decision Engine    (deterministic rules, auditable decision)
        5. Enforcement & Approval    (allow / block / quarantine / require approval)
   -> Protected tools (mock docs, mock email, mock DB, mock upload, restricted shell)
   -> Audit store + Dashboard
```

Decisions: `ALLOW | BLOCK | REVIEW | QUARANTINE`. Each decision returns `{decision, risk_score, fired_rules[], evidence[], recommended_action, latency_ms}`.

Capabilities to implement (these are the six research differentiators):
1. **Intent-based authorization:** a `TaskScope` (allowed resources/globs, allowed operations, allowed destinations, data-classification ceiling) derived from the user task. Compile it to enforceable policy. Example: "read my research folder and summarize" allows reads inside `research/`, and blocks `salary.xlsx`, emailing a file to an unknown address, and uploads (REVIEW or BLOCK).
2. **Multi-step behavioural detection:** per-session action history with a cumulative risk score. Start rule/graph-based (e.g. read doc, search for secrets, read env config, contact unfamiliar domain, upload = escalating chain). Add a scikit-learn sequence/anomaly model later as an *ablatable* component.
3. **Dynamic permission reduction:** when cumulative risk crosses thresholds, automatically shrink the session's capabilities (disable network egress, restrict files to the original project folder, disable shell, require approval for DB queries). Make the reduction ladder configurable and logged.
4. **Data lineage and exfiltration tracking:** classify data on entry (secret/PII/confidential patterns plus labels), propagate taint through agent context to outputs, evaluate destination trust, enforce egress policy. Example: `confidential.pdf -> context -> report -> external upload = block`.
5. **Explanatory human approval:** approval requests state the requested action, risk level, and the specific violated policies in plain language (e.g. "user only authorized reading and summarizing", "destination not on approved list", "file classified confidential", "would leave the local environment"), with a recommended action.
6. **Tamper-evident audit log:** append-only, hash-chained records (each entry includes the hash of the previous one), with a verify command that detects edits or deletions.

## 4. Stack

- Backend: Python 3.11+, FastAPI, pydantic v2.
- Policy: start with a pure-Python deterministic rules engine behind a `PolicyEngine` interface. Add an **Open Policy Agent (Rego)** backend as a second implementation of the same interface, so the paper can state the policy is engine-agnostic. Do not make OPA a hard dependency of the first milestone.
- Agent: LangGraph for the demo agent; also a **scripted deterministic agent** that replays labelled episodes (needed for reproducible experiments without LLM variance).
- Tool protocol: MCP-compatible tool wrapping so the gateway can front MCP servers.
- Storage: PostgreSQL (policies, agents, audit), Redis (session and short-term risk state). SQLite plus in-memory fallbacks for local dev and tests so `pytest` runs with no services up.
- Frontend: Next.js + TypeScript + Tailwind + Recharts.
- Packaging: Docker Compose for the isolated experiment environment (no outbound internet for the agent/tool containers).
- Dev machine is Windows 11; keep all scripts working in PowerShell and Docker, and avoid bash-only assumptions.

## 6. Benchmark and experiments (the main academic contribution)

Build **IntentGuardBench**, a labelled, reproducible dataset of episodes. Each episode is a YAML/JSON file: user task, granted permissions, synthetic environment, the agent's action trace, and a ground-truth label per action.

Scenario classes: **benign**, **malicious**, **ambiguous/benign-but-unusual**. Categories: legitimate tool calls, unauthorized file access, indirect prompt injection (injected text inside synthetic documents), data exfiltration, privilege escalation, credential discovery, multi-step attacks, benign unusual behaviour. Map each malicious scenario to the OWASP Top 10 for Agentic Applications (2026) category (goal hijack, tool misuse, identity/privilege abuse, unexpected code execution, memory poisoning, etc.). Verify the current category names from the OWASP source before hard-coding them.

Target 300 to 1,000 episodes as an initial goal, with several attack variants per category. Treat that as a starting point, not a justified sample size; report confidence intervals (e.g. Wilson) and note limitations.

Configurations to compare:
1. Unprotected agent
2. Static permissions (allowlist/RBAC)
3. An existing open-source baseline guardrail (investigate and pick a real one: e.g. NeMo Guardrails, LlamaFirewall, Llama Guard. If I wrote an unfamiliar name earlier, treat it as unverified and ask me before assuming)
4. IntentGuard full

Ablations: no intent analysis, no behaviour analysis, no data-flow analysis, all on. Also integrate with **AgentDojo** as an external validity check if feasible; confirm its current API before relying on it.

Metrics (computed by code, written to CSV/JSON, rendered to tables by script): Attack Success Rate, Detection Rate, False Positive Rate, Precision, Recall, Authorization Accuracy, Detection Latency (p50/p95), Task Completion Rate, Data Exfiltration Rate. Every run records seed, git commit, and config hash so results are reproducible with one command.
