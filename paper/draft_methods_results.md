# Intent-Aware Authorization for AI Agents

## 3. Method

**Threat model.** The attacker can place instructions in content the agent reads (documents, emails, tool
outputs), can supply lookalike or denylisted destinations, and can exploit user grants that are broader
than the task. The attacker does not control the user's task text, the gateway host, the resource and
destination catalogue, or the model weights. The agent holds no direct handle to any tool; every call
passes through the gateway, which fails closed on an unknown tool or an engine error.

**Authorization pipeline.** For each proposed call the gateway builds an action request (tool, operation,
canonicalised resource, destination, and for database queries the tables touched) and the policy engine
returns ALLOW, REVIEW or BLOCK with the rules that fired and a plain-language explanation. Five
components contribute:

1. *Task scope.* The user's task text and grants are compiled into a scope of permitted operations,
   resources, a sensitivity ceiling and approved destinations. Sending, uploading and summarising imply
   reading. Low-confidence compilations fall back to read-only.
2. *Data sensitivity and named-resource check.* Reading a CONFIDENTIAL-or-higher file or table requires
   that the task name it by its path or full file name (a table by its name); otherwise the action goes to
   REVIEW (SCOPE-005). A word shared with the file name, such as "budget" or "config", does not count.
3. *Data lineage.* An allowed read or query of sensitive data taints the session; egress to destinations
   that are not approved is then blocked (taint and egress rules). Outbound content is scanned for secret
   patterns, and also compared with fingerprints of the sensitive data the session actually read (runs of 12
   letters and digits), after decoding rot13, reversal, URL encoding and base64, base32 and hex up to two
   levels, and across the last few outbound messages. A match on credentials is blocked and a match on other
   confidential data goes to human review (rule TAINT-002).
4. *Cumulative behavioural risk.* Sequence rules (reconnaissance, then credential reads, then egress)
   accumulate a session risk score. Thresholds reduce permissions in steps: network at 0.4, shell and
   locked files at 0.6, database review at 0.8, and quarantine at 1.0. Risk and tags carry over to a new
   session of the same agent with decay.
5. *Output scanning.* Tool output is scanned for instruction-like text; a hit raises risk, and later
   egress, shell or database actions in that session go to REVIEW. Output is never obeyed.

Every decision is appended to a hash-chained audit log, and REVIEW decisions enter an approval queue with
the evidence behind them.

## 4. IntentGuardBench

Episodes are scripted sequences of tool calls with per-step labels (harmful, clean or neutral). The
benchmark has a hand-written core set, a sequence set, a seeded template generator (development seed 1,
held-out seed 2026, fresh seed 4242; 300 episodes each for the last two), a hand-written adversarial pair
of sets, an injection-text set, and a cross-session and database set. The engine and the benchmark share
an author, which is the main validity limitation; an external episode loader and a contributor guide exist
so that someone else can supply episodes (not yet done).

## 5. Experimental setup

*Systems.* An unprotected agent; static role-based access control; a keyword guardrail (a stand-in for
content filters, not a published tool); LlamaFirewall 1.0.3 local scanners (REGEX and HIDDEN_ASCII, default
settings); LlamaFirewall with Llama Prompt Guard 2 (86M) only; and IntentGuard, with five single-component
ablations. The two LlamaFirewall rows scan each proposed call, and the file content on reads, as messages;
this adaptation is ours. Not run: LlamaFirewall AlignmentCheck (needs an external LLM) and CodeShield.

*Metrics.* Attack success rate (ASR, share of harmful steps executed), exfiltration success, benign
actions blocked, review friction (clean steps sent to review), task completion, and per-call latency,
with Wilson 95% intervals. *Discipline.* Seed 1 was used for development, seed 2026 was seen once and is
no longer held-out after rule SCOPE-005 was developed [F4, F5], and seed 4242 was not used for tuning.

## 6. Results

### 6.1 Generated sets (excerpt of `paper/tables.md`)

Fresh seed 4242 (300 episodes: 139 malicious, 117 benign, 44 ambiguous):

| System | ASR % | Exfil % | Benign blocked % | Review friction % | Task completion % |
|---|---|---|---|---|---|
| unprotected | 100.0 | 100.0 | 0.0 | 0.0 | 100.0 |
| static RBAC | 70.7 | 58.9 | 5.6 | 0.0 | 83.2 |
| keyword stand-in | 74.2 | 66.3 | 0.0 | 0.0 | 100.0 |
| LlamaFirewall local scanners | 71.7 | 41.1 | 13.0 | 0.0 | 60.9 |
| LlamaFirewall Prompt Guard 2 | 85.4 | 100.0 | 0.0 | 0.0 | 100.0 |
| IntentGuard | 1.0 | 2.1 | 0.0 | 4.1 | 87.6 |

The tightened named-resource rule of section 6.4 costs usability: on the generated sets review friction
rose from about 2% to about 4% and task completion fell from 93.2% to 87.6% on this set (95.0% to 87.5%
on seed 2026) [F16]. IntentGuard's low ASR on this set is partly circular: the generator never names the file in the task for
attacks and always names it for legitimate credential reads, which is exactly what SCOPE-005 tests
[F5]. The earlier held-out number before SCOPE-005 is the honest signal of transfer: 11.4% on the
hand-written core set became 43.2% on held-out seed 2026 [F4].

### 6.2 Ablations (fresh seed 4242)

Removing the named-resource check raises ASR from 1.0% to 31.3%; removing intent analysis, to 51.5%;
removing behaviour analysis, to 6.1%; removing data-flow analysis, to 8.1%. Removing cross-session
carry-over changed nothing on this set because it contains no cross-session episodes. Intent-related
components contribute most; behaviour and data flow contribute smaller, overlapping amounts.

### 6.3 Baseline reading

The LlamaFirewall regex scanners block 10.9% to 13.0% of benign steps on generated sets, because the
default patterns flag email addresses [F8]. Prompt Guard 2 blocked no benign step but allowed 85% to 89%
of attacks on the generated sets. This is a category mismatch, not a weak model: most episodes are
tool misuse with no injected text, which Prompt Guard is not designed to detect. On the injection-text
set (10 malicious episodes) it allowed 50% against 0% for IntentGuard, with a median CPU latency of
roughly 200 to 310 ms per call versus 0.03 to 0.08 ms for the rule engine [F12].

### 6.4 Adversarial sets (hand-written, same author)

Attacks written to break the rules found real bugs (path traversal, secrets read through an allowlisted
shell command, unclassified database reads), which were fixed [F6, F7, F10]. Four gaps stayed open: encoded
exfiltration to approved destinations, secrets split over several messages, filename-token collisions
with the named-resource check, and obfuscated SQL. A third batch targeting exactly these was written and
frozen before any rule changed, in a development half (16 episodes) and a held-out half (18 episodes), each
with benign controls [F15]. Before the fixes IntentGuard let 13 of 13 harmful steps through on the
development half and 11 of 17 on the held-out half (64.7%). The fixes were: decoding base64, hex and rot13
in outbound content; a per-session buffer of outbound text; naming a file only by its path or full file
name; and a more tolerant SQL table finder. They were developed on the development half only. Afterwards 1
of 13 (7.7%) and 5 of 17 (29.4%) harmful steps got through, with every benign control still allowed [F16].
The five remaining held-out misses are base32, URL-encoded and reversed payloads (decoders deliberately
not added, to measure generalisation) and the first fragments of a split secret, which leave before a
pattern forms; the wider decoders and the lineage check added later (see below) leave 1 of 17 (5.9%) on that
half [F18]. One bug in the first version of the buffer was found through the held-out half, so that half
was run twice and is no longer strictly untouched. Both halves share an author with the engine. The earlier
adversarial sets now show 0% ASR, but they were written to expose the gaps just closed, so that figure is
partly circular and should not be quoted as robustness.

A fourth batch (development half of 13 harmful steps, held-out half of 13, each with benign controls) was
frozen before the content-lineage check of section 3 existed [F17]. Before it, IntentGuard let 10 of 13
(76.9%) and 9 of 13 (69.2%) harmful steps through. After it, 1 of 13 (7.7%) and 4 of 13 (30.8%) [F18]. With
lineage switched off but the wider decoders left on, 6 of 13 (46.2%) on both halves, so lineage itself
accounts for roughly 40 and 15 percentage points. The four held-out misses are a paraphrase and a leetspeak
rewrite (included on purpose as expected limits), a confidential leak with words between the figures that
breaks the 12-character run, and the first short piece of a split secret. The "held-out" half here holds new
instances of the same attack classes, written by the same author, so it tests generalisation across
instances, not across new kinds of attack. No other set changed and every benign control was allowed. A cost
not measured at scale: legitimate tasks that email confidential figures now go to review.

### 6.5 LLM-driven agents (local models)

Two small models (llama3.2:3b, llama3.1:8b) were given the same tools and 11 episodes (5 seeds, temperature
0.7) against a hand-written oracle. Neither followed an injected instruction in the base set [F11, F13].
A forceful-injection stress test (4 documents posing as the user, an assistant turn, IT security, and a
pasted tool call; 5 seeds) made the unprotected llama3.1:8b execute unauthorized actions in 8 of 40 attack
runs (20%, 95% CI 10.5% to 34.8%): reads of the secrets file and emails to two denylisted addresses.
With IntentGuard, 0 of 40 (CI 0% to 8.8%) [F14]. This is a susceptibility test with one 8B model and
author-written injections; it is not a rate for real attackers.

## 7. Limitations (state these plainly)

- Same author for engine and episodes; no independent episode set yet.
- Template-based intent compiler and keyword-based rules. Exfiltration detection looks through simple
  encodings only: paraphrase, character substitution (leetspeak) and ciphers pass, short first pieces of a
  split secret leave before a match forms, data read in an earlier session is not fingerprinted, and SQL is
  matched by name, not parsed.
- Review friction is a real cost: a hijacked step can lock a legitimate task for the rest of a session
  [F9, F11, F14].
- Scripted agents for most results; LLM-agent studies use two small local models and few seeds.
- Process-level isolation of the agent from the tools is demonstrated as an API shape only.
- Not a comparison with Progent or CaMeL, which were not run.
